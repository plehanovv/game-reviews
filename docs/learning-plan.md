# Как будем разрабатывать

## Формат совместной работы

На каждом шаге: обсуждаем небольшую задачу и критерии готовности → ты пишешь
решение → разбираем дифф → исправляешь замечания → проверяем → делаешь коммит.
Я объясняю новые понятия, предлагаю варианты и помогаю с ошибками.
Готовую реализацию очередной функции пишу только по твоей просьбе.
Задача — научиться объяснять свои решения и менять код самостоятельно.

## Оценка проекта

Полноценный аналог игрового медиа с социальной сетью — большой продукт.
Помимо API ему нужны интерфейс, модерация, управление контентом, поиск,
защита аккаунтов, резервное копирование и эксплуатация. Поэтому первая
версия: каталог → аккаунт → личная библиотека → оценка и рецензия.
Новости, посты, подписки, комментарии и рекомендации — последующие этапы.

Для учебного MVP разумно планировать месяцы работы с частичной занятостью;
срок сильно зависит от текущих знаний и глубины интерфейса. Полный аналог
не стоит считать небольшим CRUD-проектом.

Начинаем с модульного монолита: один процесс и одна основная база,
пакеты по предметным областям появляются по мере необходимости.
Микросервисы пока не дают пользы, сопоставимой со сложностью их эксплуатации.
HTTP-обработчик отвечает за протокол; бизнес-правила со временем вынесем
в сервис; SQL — в репозиторий. Не будем заранее создавать пустые слои
и интерфейсы для каждой структуры.

## Роль стека

| Инструмент | Практическая задача | Чему учимся |
| --- | --- | --- |
| Go | HTTP API и фоновые обработчики | Ошибки, context, интерфейсы, конкурентность, тесты |
| PostgreSQL | Игры, пользователи, оценки, рецензии | SQL, ограничения, индексы, транзакции, миграции |
| Redis | Кэш популярных карточек с TTL | Cache-aside, инвалидирование, работа при сбоях |
| Kafka | События рецензий для фоновой обработки | Группы потребителей, повторы, порядок, идемпотентность |
| Docker | Воспроизводимое локальное окружение и сборка | Сети, volumes, healthcheck, образы |
| Git | Небольшие проверяемые изменения | Диффы, ветки, коммиты, ревью |

PostgreSQL остаётся источником истины. Redis можно потерять и восстановить.
Kafka подключаем, когда появится настоящий асинхронный сценарий.
Запись рецензии в БД и публикация события — две операции, между которыми
возможен сбой. На соответствующем шаге разберём transactional outbox:
изменение и событие сохраняются одной транзакцией в PostgreSQL, затем
worker публикует событие. Повторная доставка требует идемпотентного consumer.

## Этапы и критерии готовности

1. **HTTP и Git.** Запуск сервера, маршруты, JSON, коды ответа, первый коммит.
   Готово, когда можешь объяснить путь запроса и добавить простой обработчик.
2. **Каталог в памяти.** Модель игры, список и получение по ID, 404 и валидация.
   Сначала маленький вертикальный срез; временное хранилище явно обозначаем.
3. **PostgreSQL.** Подключение через pgx, миграции выбранным инструментом,
   таблица игр, SQL-запросы, pagination и интеграционные тесты с реальной БД.
   После перезапуска данные сохраняются, миграции применяются с чистой базы.
4. **Аккаунты.** Хеширование паролей, сессии, вход/выход, права доступа.
   Для браузера обсудим cookie, CSRF и XSS; пользователь не меняет чужие данные.
5. **Личная библиотека и рецензии.** Статусы игры, рейтинг, редактирование.
   Обсудим шкалу оценок, одну оценку на пару user/game и ограничения БД.
6. **Интерфейс.** Для начала можно взять Go html/template и HTML/CSS;
   необходимость отдельного frontend-приложения обсудим перед реализацией.
   Пользователь проходит основной сценарий из браузера.
7. **Redis.** Кэш чтения каталога, TTL и инвалидирование при изменении.
   Недоступность кэша не ломает корректность основных данных.
8. **Kafka.** Outbox и worker, например для ленты активности по рецензиям.
   Проверяем повторную доставку и восстановление после сбоя.
9. **Эксплуатация.** Readiness, метрики, нагрузочные проверки, резервные копии
   и пробное восстановление. Затем развёртывание и расширение социальных функций.

Перед каждым этапом уточняем контракт и пишем тесты значимого поведения.
Не нужно изучить весь стек заранее. Для начала достаточно функций, структур,
срезов, методов и ошибок Go; HTTP, SQL и инфраструктуру осваиваем по задачам.
Отдельно потребуется выбрать законный источник описаний и обложек игр;
на старте используем собственные тестовые данные.

## Твоё первое задание

1. Открой корень проекта в GoLand и запусти `go run ./cmd/api`.
2. Вызови `/healthz` и прочитай `main.go`, `config.go`, `router.go`.
3. В `internal/httpapi/router.go` добавь `GET /api/v1/about`.
   Ответ: HTTP 200, JSON `{"name":"game-reviews","version":"0.1.0"}`,
   заголовок `Content-Type: application/json; charset=utf-8`.
   Для сериализации попробуй `encoding/json`, а не ручную склейку JSON.
4. Добавь проверку нового маршрута в `router_test.go`: статус, тип содержимого
   и поля JSON. Сравнивай данные после декодирования, чтобы порядок полей
   и пробелы не влияли на результат.
5. Выполни `gofmt -w cmd internal`, `go test ./...`, `go vet ./...`.

Критерий готовности: маршрут работает, проверки проходят, ты можешь объяснить
`http.ResponseWriter`, `*http.Request` и назначение HTTP-заголовка.
После этого напиши «готово, проверь» или покажи ошибку, которую хочешь разобрать.

После ревью создадим Git-репозиторий и первый коммит вместе: разберём
`git init`, `git status`, `git diff`, staging и `git commit` на этих файлах.
Удалённый репозиторий для первого упражнения не нужен.
